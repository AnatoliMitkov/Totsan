# Totsan SEO, Sitemap, GA4, and Search Console

## Architecture

- Route rules and canonical path normalization live in `src/lib/site-routes.js`.
- Shared metadata management lives in `src/lib/seo.js`.
- Static routes get default metadata from the router, while dynamic public pages override it with real page data.
- GA4 initialization, consent gating, page views, and safe events live in `src/lib/analytics.js`.
- The canonical sitemap endpoint is served by `api/sitemap.xml.js` and generated by `src/lib/sitemap.js`.
- Local SEO validation runs through `npm run validate:seo`.

## Sitemap architecture

- Static URLs are generated from known public routes, the five layers, and the static product catalog.
- Dynamic URLs are fetched at request time from public Supabase data for published profiles and approved published partner services.
- Shared project URLs are excluded because they are private/share-token pages.
- Query strings, admin routes, inbox, orders, checkout, and account areas are excluded.
- `robots.txt` points to `https://totsan.com/sitemap.xml`.

## GA4 setup

Required frontend env vars:

- `VITE_GA_MEASUREMENT_ID`
- `VITE_GA_REQUIRE_CONSENT`

Recommended values:

- `VITE_GA_MEASUREMENT_ID=G-...` in Vercel only
- `VITE_GA_REQUIRE_CONSENT=true` until a real consent UI is wired

Behavior:

- The app no longer hardcodes the GA ID in source control.
- Analytics does nothing if the measurement ID is missing.
- Analytics also stays disabled unless consent is granted, unless `VITE_GA_REQUIRE_CONSENT=false` is explicitly chosen by the owner.
- Automatic page views cover canonical public route changes.
- Dynamic public detail pages send page views only after the real content title is known.
- Private route details are not auto-tracked.

## Vercel setup

Set these environment variables in Vercel:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY` or `VITE_SUPABASE_PUBLISHABLE_KEY`
- `VITE_SITE_URL=https://totsan.com`
- `VITE_GA_MEASUREMENT_ID`
- `VITE_GA_REQUIRE_CONSENT=true` or `false`

Notes:

- The sitemap runtime uses only public Supabase environment variables.
- Do not use a service-role key for sitemap generation.

## Adding future SEO

For future public profiles:

- keep `slug`, `name`, `tag`, `city`, and descriptive text populated
- ensure `is_published=true`
- the page metadata and sitemap will pick up the profile automatically

For future public services:

- keep `slug`, `title`, `subtitle` or `description_md`, `is_published=true`, and `moderation_status=approved`
- FAQ entries on the page become FAQ structured data automatically

For future products:

- add the product to the static product catalog metadata
- product routes and sitemap entries are generated from that catalog

For future portfolio project detail pages:

- add a real public route first
- extend `src/lib/site-routes.js`, `src/lib/sitemap.js`, and the relevant page SEO config
- do not reuse the shared-project route for indexable portfolio pages

## Local and post-deploy testing

Local checks:

1. `npm run build`
2. `npm run validate:seo`

Manual browser checks:

1. Open a public page and inspect the rendered `<title>`, canonical, description, OG tags, and JSON-LD.
2. Navigate between public routes and confirm metadata changes.
3. Navigate to private routes and confirm `noindex, nofollow` is applied.
4. Confirm `https://totsan.com/robots.txt` and `https://totsan.com/sitemap.xml` after deployment.

Analytics checks:

1. Confirm consent is granted by the real consent mechanism or by the agreed runtime integration.
2. Open GA4 DebugView or Realtime.
3. Visit `/`, `/start`, `/katalog`, a real profile page, a real service page, and a real product page.
4. Trigger one inquiry, one chat intent, and one checkout start in a safe test flow.

Known limitation:

- This is still a client-rendered SPA. Invalid dynamic URLs can look like soft 404s to crawlers because the HTTP response is still `200` from the SPA shell. Fixing that requires a separate SSR, prerender, or edge-routing phase.
